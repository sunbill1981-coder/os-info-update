# 工程师报告阅读指引

适用于0.5.0-dev分层报告。报告帮助团队判断哪些Windows外部变化值得核对，不代表产品已经受影响，也不代表已经执行测试。生成与主题字段的操作契约见 [主题评审指南](../skills/windows-os-intelligence/references/engineer-report.md)。

## 从哪里开始

从运行结果中的 `engineer_report.index` 打开行动摘要，或使用对应用途空间的 `reports/latest-engineer.html` 导航。`reports/latest.html` 是旧格式全量报告；新包内的 `archive.html` 也保留完整活动库。

先检查用途、报告窗口和覆盖说明，再看“需要行动”“需要验证”。首页默认展开最多5个就绪主题；超过预算的事项会列出数量和链接，重大事项另有数量提示。这个数字是阅读预算，不是风险数量上限或安全结论。预算可以通过配置调整，少于5项时不凑数。

持续关注主题及全部主题在独立入口中保留。没有经过评审的主题时，报告会明确说明，并保留高关注待补证据线索。当前已有数据中的高关注线索被覆盖，不代表所有档案均完成深度评审或外部来源没有遗漏。

## 每个主题如何使用

| 看到的信息 | 工程师如何判断或操作 |
|---|---|
| 风险与条件 | 核对Windows版本、角色、补丁、应用及配置是否与本环境相交；不要只因同属Windows或云桌面就认定适用 |
| 为什么现在关注 | 区分新变化、已有问题未覆盖修复、持续事项及证据修订；窗口内更新日期不自动代表影响升级 |
| 先做 | 按指定对象取得首份记录，如版本/配置/补丁清单；这是开始核验的入口 |
| 承接角色 | 找对应组件或测试负责人；角色名称不等于任务已实际分派 |
| 证据状态 | 官方记录确认的是外部事实；“内部适用性未知”表示还需核对本环境 |
| 主题详情 | 按条件与步骤执行最小核验，保存指定记录，再按结果处理建议跟进 |

先判断条件，再选择代表环境操作。条件不匹配时保存排除依据；匹配但未复现时记录实际基线和测试组合；复现或发现未覆盖修复时，交给组件负责人评估受影响子集与处置。未复现只能说明已测试组合，不能直接关闭所有版本的外部风险。

如果首步缺少可执行对象、版本条件或必要说明，反馈具体缺项给情报负责人。缺外部原文/范围属于补证据工作；缺内部版本/配置属于适用性核对，不需要等整个产品支持矩阵整理完才开始。

## 如何读时间线

“最早可追溯信号”表示已保存并审阅的证据目前能追溯到的日期。说明为官方Opened日期时，只能称为该官方问题的建档时间，不能认定全球首次发现。新增更早证据后日期可以修订，主题身份和旧判断仍保留。

“影响扩大迹象”与“大规模爆发”分开。后者需要明确的规模及日期证据；多个帖子、微软首次确认、KEV收录或“已被利用”均不能单独证明大规模爆发。“未知／尚未证实”表示缺少足够证据，不表示风险没有发生。

约束收紧优先看公告与强制生效，功能变化优先看发布/推出范围；缓解和修复也分开，并注意部分修复及各Windows版本的差异。采集日期、评审日期和报告日期不能替代风险日期。读取今天的网页回填历史月份，不等于恢复当月月底已知信息，也不能据此计算提前预警天数。

## 为什么多个事件会放在一起

同一问题的多来源或多平台观察可以归为同一风险。不同风险共用一个首步核查任务时，可组织为一个验证批次，但每个风险的适用范围、动作和结果仍要分别判断。

一个补丁可能涉及多个互不相关的问题；同一症状也可能有不同原因。共同KB、组件或症状不能单独证明同源或跨期联动。A+B联合风险需要另外核对共同生效的版本、配置、阶段与机制，主题归并不能代替这项判断。

## 完整信息与分享

主题详情链接到全部关联事件和原文依据。完整档案提供所有规范化事件；`data/events.ndjson`保存事件数据，`data/themes.json`保存当前主题及可用修订，`data/event-themes.json`保存反向关联，`coverage.json`记录窗口、用途、数量和缺口。

分享整个ZIP或完整报告目录。解压后打开 `index.html`，保留 `topics/`、`data/`、`archive.html` 等相对位置，避免单独发送首页造成链接失效。包内内容可离线阅读，外部原文链接需要联网；完整采集网页快照仍保留在原运行空间，ZIP中不包含这些网页。

已发布报告保留为快照。后续证据或分析变化生成新包；持续主题保留稳定标识与修订记录。源事实变化、基线证据缺失或历史重评可能使原主题降回待补证据，需重新审阅。

debug、trial、production是运行用途；candidate、approved是数据验收状态，两者分别判断。运行成功、生成HTML或上传GitHub，都不能单独使数据成为正式基线。试跑数据默认留在本地，正式历史包另行验收和上传。

## 试点反馈记录

最小反馈包含主题标识、实际Windows/补丁/配置、条件是否匹配、首步是否清楚、实际执行内容与记录、结果、后续负责人。未执行就写未执行；无法判定就写缺少什么信息，不把外部已确认转述为内部已复现。

建议由情报负责人核对来源和主题，测试协调人分派匹配场景，组件工程师执行并反馈。周报/月报是分享节奏，未关闭事项继续跟进，重大变化不应仅因等待月报而搁置。上述分工是运营建议，不是已安装的调度或已发送的任务。
