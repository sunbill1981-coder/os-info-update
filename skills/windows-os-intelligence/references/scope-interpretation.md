# 公开适用范围与基线核验

## 两种架构不要混淆

`cpu_architectures` 指 ARM、ARM64、x64、x86 等 CPU 范围；`delivery_architectures` 指 VDI、IDV、TCI/VOI、VAPP 等产品交付形态。VDI 不能代替 x64，也不能证明某个 ARM 问题适用于 VDI 所有来宾系统。

## 数据与证据

`affected_scope` 是 `scope-v1` 版本的原文范围提取结果，包含 CPU、产品—CPU 对应、特定应用、条件线索、排除范围、可识别症状及逐项原文摘录和链接。发布健康采集器在截断摘要前读取完整问题正文。多页面去重保留各页的范围证据；MSRC 的架构匹配按产品进行，不能把某个 Server 的 x64 范围套给另一个 Windows 客户端。

规则位于 `config/scope-rules.json`，应用别名与通用语法可扩展，不按特定 KB、CVE、问题编号触发。解析是保守的、非穷尽的，不支持的应用名称或复杂条件仍须读原文。普通“64-bit”不能直接认定为 x64；缓解步骤中顺带提及架构不能自动变成影响范围。

## 核验状态

`applicability_review` 使用 `applicability-v1`，针对已启用资产队列给出：

- **匹配**：已提取的 Windows 产品、角色、CPU、应用和条件与声明基线相交；不等于确认受影响或测试通过。
- **不匹配**：某个已明确维度与声明基线不相交，例如公开 ARM 范围与已确认 x64 基线。仅针对该事件公开范围，不宣称该平台绝无其他风险。
- **未知**：未提供具体基线，或 CPU／应用／条件未明确。产品组合相关度再高，也不能替代适用性核验。

本阶段不改数值风险模型、不自动隐藏或归零不匹配事件、不将新字段单独升级为群告警。旧的 `asset_matches` 是粗粒度版本／角色候选队列，可与“不匹配／未知”并存；人读时以范围核验说明为准，不把候选数量当成精确受影响资产数。

条件线索不一定是必要条件：例如新镜像“较易触发”或应用更新作为缓解前提。不得因某条线索为 false 就自动排除。`not known to be affected` 按“未发现已知影响”保留，不能转译为“明确不受影响”。Edition、Build 范围、KB 与复杂配置仍须原文和专项验证，不在该状态中宣称全面核验通过。

## 结论与行动边界

标题和公开事实摘要优先保留具体应用、症状和 CPU；影响与测试先限定公开范围。特定应用启动故障应先测试该应用启动、登录、退出和重启，对照补丁与应用更新状态。不能只因正文出现新镜像就断言金镜像封装、克隆、加域失败，不能把某一应用故障改写成所有应用、宿主机或桌面池不可用。

HTML 顶部范围提示、事实摘要、适用性和四个行动区域默认显示；逐项原文摘录放在折叠证据链。任何摘要或建议都保留可直达来源；建议是工程推演，不代表微软已给出内部测试结论。

分补丁阶段的验证同样限定 CPU／应用范围。特定应用回归在引入前、引入后未修复、修复或缓解后均围绕指定应用验证，不另套完整克隆、域加入或长会话矩阵。

## 兼容与发布

新字段有默认值，历史记录可直接读取，无 SQLite 表结构迁移。它们属于版本化派生评估字段，现有事实指纹、事件 ID 和告警指纹保持不变。补全范围可能产生“评估变化”，不是新增故障；报告应如实呈现，不发送历史群告警。范围变化本身目前不独立触发群提醒，需在后续告警策略改版中单独评审。

对已有数据库先用 SQLite backup API 建立一致性备份；重新采集后观察新增、事实变化、评估变化。不要将历史源事实重新标记为新问题。保持私有环境画像为空，直到使用者提供真实基线；不上传运行报告、资产数据或凭据到公共仓库。
