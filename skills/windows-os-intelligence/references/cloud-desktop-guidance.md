# 云桌面外部风险判断与行动建议

默认交付“完整事实库 + 少量值得核验的外部风险摘要”。目标是在客户暴露于风险之前提供有行动价值的线索；不是为每条 CVE 自动派发一套测试与上线门禁。无内部资料时也应完成外部判断，把内部适用性保留为未知。

## 选择值得核验的线索

共同观察约束收紧与支持边界变化、生态故障、新特性与默认行为变化，以及其它缺陷和安全风险。普通企业 PC 上的认证、网络、启动或应用异常也可能揭示云桌面依赖的 Windows 行为；不得只保留标题含 VDI 或厂商名的报告。

根据公开证据说明潜在影响的严重性、触发条件、涉及的工作流、变化所处阶段及核验价值。来源权威程度决定结论可以说多确定，不单独决定是否值得调查。单条可信的一手报告也可以成为“待核验线索”，但不能据此宣称根因、微软确认或内部受影响。适用产品不明时优先补公开范围或触发条件，不把未知转换成低风险。

每条入选摘要回答：

1. **外部发生了什么？** 用中文概括变更或报告症状，保留版本、状态、时间、来源与证据。
2. **为什么值得云桌面关注？** 说明可能共享的组件、工作流或条件；这是假设，不是内部命中结论。
3. **目前能确定什么，还缺什么？** 区分事实、用户报告和工程推演，保留内部适用性未知项。
4. **最小的下一步是什么？** 先由 Skill 核验可取得的外部正文与修订，再给出具体检查对象、检查内容和判定后的动作。确实缺少外部证据时，写明尚缺哪条事实及补证路径；不能把一组泛泛问题当作工程核验计划，也不强制每条都执行产品测试。
5. **何时需要复查？** 写明新的独立报告、官方范围变化、功能进入默认启用／正式发布等复查条件；如建议日期，明确它尚未自动调度。

摘要受阅读预算限制时，保留未入选事实和筛选理由；“未入选”不等于安全。只有证据和产品条件足够、或用户要求测试设计时，再展开场景、验收观察、灰度与回退建议。月报适合汇总议题变化和未决事项，不代表日常高价值线索已得到及时处理。

## 跨期判断的行动与反馈

组合风险可以基于窗口外的约束与多个变化，本期新认识不改变旧公告日期。按 [跨期评审契约](pre-release-operations.md#2-每轮必须做的跨期评审) 保存共同生效依据、排除条件、待补信息及具体操作；共享组件不是机制证明。风险卡片和本期事件摘要有各自可配置的阅读预算，溢出仍需继续评审。

建议与实际执行分开：执行结果通过私有 feedback-v1 保存，引用实际对象修订与测试基线。旧结论需重审时保留原结果，不自动关闭所有范围、不把测试结果改写成 Windows 公告。报告展示反馈数量，详细事项保留在本地 triage.continuity.feedback 中。

## 最小核验计划

每条入选 `triage` 事项使用 `verification_plan` 描述下一步，不能仅写“核对是否受影响”“执行回归测试”或把外部事实核验全部转交给读者。计划基于已核验的来源条件和业务动作；只需完成能推进一次判断的最小工作，不生成整套产品测试。

计划须明确以下五步，并把缺少输入单列：

1. **适用条件**：列明原文支持的系统、版本、组件、触发配置、实施阶段与排除边界；未知不等于全部适用，也不等于可排除。
2. **先检查什么**：指出要查看的具体对象与字段，并说明与哪条来源条件比对。例如，先读取候选镜像的系统构建、相关组件版本及实际启用状态，再判断是否满足该事件前提。只保留本事件需要的字段；未核验的命令、策略名、注册表项或查询路径不能编造。
3. **命中后的最小对照**：在适用条件成立时，围绕来源明确的操作或行为设计一个对照，保持其它条件一致，只改变待验证的更新或配置，并给出要观察的结果。没有明确触发动作或尚缺必要输入时，先补证，不伪造复现步骤或验收阈值；建议不等于授权执行配置变化。
4. **记录什么**：列出使结果可复核的必要字段，例如实际基线标识、相关版本与状态、触发步骤、对照前后表现、错误及发生时间。仅在有出处或确定可获取时点名日志；避免要求与本事件无关的全套记录。
5. **结果后续动作**：分别说明条件不匹配、条件匹配且出现异常、未出现异常、输入不足时如何处理。排除只覆盖已核对组合；未复现不等于风险不存在；对照异常仍需分析原因，不能直接证明补丁因果或全产品受影响。结论涉及变更或对外通知时，仍遵守原有授权边界。

`verification_plan` 使用以下结构，HTML 与 Markdown 按此展示具体计划；旧 `questions` 字段仅供机器消费者兼容，不再作为人用“最小核验”的替代内容：

| 字段 | 契约 |
| --- | --- |
| `schema` | 固定为 `verification-plan-v1`。 |
| `status` | `待补外部证据` 或 `待核对内部范围`；不把“待核验”写成已验证。 |
| `owner` | `情报分析` 或 `产品研发或测试`；只是建议承接阶段，不表示已经分派。 |
| `suggested_role` | 可选的具体建议角色，例如相关组件的兼容测试工程师；不编造姓名。 |
| `first_action` | 一条可以开始执行的具体动作；受输入限制时，点明首先取得的必要输入和用途。 |
| `scope` | 字符串列表，保留来源适用条件、排除条件和未知范围。 |
| `steps` | 字符串列表，按先检查、条件命中后最小对照的顺序组织。 |
| `record` | 字符串列表，仅列本次判断需要保留的字段。 |
| `decisions` | `{when, then}` 列表：可观察的判断条件及对应后续动作。 |
| `missing_inputs` | 字符串列表，具体说明尚缺的外部事实或内部输入，不用空泛问题凑数。 |
| `basis` | `{label, url}` 列表，直达本计划依据的来源；链接支持事实，不代表来源作者提出了同一工程建议。 |
| `executed` | 固定为 `false`。生成或核验计划内容不等于已经执行实验。 |

进入 `待核对内部范围` 需有已核实来源日期，并声明 `scope_verified: true` 和非空 `scope_basis`，说明公开范围如何按原文核验。这些字段只记录外部范围复核，不证明内部产品命中。缺少复核依据时先进入 `待补外部证据`。`basis` 只能引用该事件已有原始来源或 `source_references`，新来源应先补入核验证据链。

内部版本、环境或实施细节可以缺失。此时继续完成外部风险收集及事实判断，只限制依赖这些输入的后续动作，不能因此阻塞整轮采集。计划与公开事实分开标注为工程建议，不改变事实指纹、来源权威程度、正式告警或通知授权。

## 事实与推演边界

- “公开事实摘要”只使用已入库且明确标注来源状态的事实／报告，必须直接链接到原文。社区内容标为“用户报告”，厂商内容标为“厂商说明”；不得把来源用户声称的确认写成微软确认，也不得把作者复现写成内部复现。
- “外部潜在影响”根据公开组件、角色、工作流和前置条件提出；“内部适用性”依赖实际产品／环境证据，二者分别呈现。“建议测试”“预防门禁”和“针对性探索”属于工程推演，必须标明“需验证”。
- 每一条推演建议都要链接到触发它的来源事实／报告，但不得暗示原文已给出了该内部测试结论。
- 不要为单一 KB、SID、TPM、错误码或某一次事故编写特权规则。生产规则应从可复用维度触发：变化类型、前置条件、工作流、症状、组件、角色与证据；内部画像仅作为可选补充。
- CPU、特定应用、条件与排除范围必须贯穿摘要和建议。来源置信度高不代表范围解析完整。按 [范围判读](scope-interpretation.md) 保留“匹配／不匹配／未知”，不要把 ARM 应用问题泛化到全部 x64 环境，也不要将新镜像上的应用故障外推为克隆或加域故障。
- 锐捷产品链路可按 [可选产品知识库](optional-product-knowledge.md) 做智能体层的补充分析。将“产品知识依据”与“公开事实”“现场已确认配置”分开；原文未读取的 AI 回答只用于待核验问题和测试候选。该补充不自动进入采集器、评分或发布器，无知识库时按现有流程完成分析。

## 事实库与详细报告的边界

离线 HTML 默认展示核验摘要及覆盖缺口，完整资料库折叠，摘要链接可直接展开并定位对应卡片。资料库保留完整分析卡和折叠的版本—补丁矩阵、产品／组件、标识与证据链。采集器另存 `run-NNNNNN.triage.json`。摘要独立排序，存量归档排序不变；不将详细卡中的建议自动转为执行任务。展开一张卡片后，部分修复、关键触发条件和补丁状态待核对提示须可见。未配置具体基线时统一说明，避免重复空资产栏；这不改变事件、现有评分、指纹或正式告警。

摘要使用“优先核验／计划核验／留存待查”等定性优先级，外部相关性使用“直接链路候选／共性流程候选／未知”等标签。它们描述公开信号的核验顺序，不表示内部受影响，也不改写正式告警状态。展示预算等通用配置位于 `config/triage.json`，可通过采集器的 `--triage-config` 选择其它配置。全量事实和独立摘要同时保留。

详细报告提供“本期阅读入口 → 分组目录 → 详细卡片”。目录按风险阶段分组，漏洞再按组件主题展开，与筛选器联动；每个目录项指向对应卡片，卡片提供返回目录入口。外部筛选可独立于现有环境评分，但不得悄然改写事件的分数或告警状态。沿用已有事件身份和报告页内编号，不引入永久 UUID。

每张卡片顶部必须明确区分“未修复时的安全风险”“更新后的回归风险”“升级／配置变更风险”或“问题触发阶段待确认”。关联 KB 不是补丁角色：按产品版本保留引入更新、修复更新、缓解措施及直达原文的对应关系，不能把跨版本 KB 拼成一条升级路径。部分修复必须注明；官方发布修复不等于内部镜像已安装或已验证。修复已被后续累计更新包含时，缺少旧 KB 编号不能直接推断未修复。

若展开测试建议，须区分补丁状态：安全漏洞的未获得修复／已安装修复／已安装后续累计更新；回归问题的尚未包含引入变更／已包含引入变更未获完整修复／已安装修复或缓解措施。阶段性建议属于工程推演，并链接到触发事实。没有资产补丁清单时，当前镜像状态统一标为待核对；不要为补全模板而生成全部组合。

预览特性不一定进入正式版，应记录当前阶段及待观察的启用条件，不直接声称升级后必然变化。查询计划、采集源成功与风险发现完成分别报告；未执行查询、访问受限、只有标题或摘要都要保留覆盖缺口。建议复查日期不是计划任务，首次发现时间不是来源发布时间；没有历史快照和客户暴露时间，不计算未经证实的预警提前量。
